# V-COF Core 2.2 — Migration and Challenge Plan

Version: `0.1.0`

Status: `DRAFT_FOR_CHALLENGE`

Authority ceiling: `PUBLIC_BRANCH_AND_DRAFT_PR_ONLY`

## 1. Objective

Provide a staged path from public candidate design to a possible future V-COF
2.2 adoption without conflating publication, internal constitutional amendment,
model migration, evaluation and production activation.

## 2. Phase model

### Phase 0 — Public drafting

Deliver the versioned public package in a dedicated branch and draft pull
request. Validate syntax, relative links, placement and authority boundaries.

Exit condition: draft PR exists, checks are reported, no merge occurred.

### Phase 1 — Challenge and nomenclature

Review the expansion of V-COF, version separation, public/private boundary,
effect classes and the Sol/Terra/Luna profile semantics.

Exit condition: objections, accepted changes and unresolved issues are recorded
against an exact candidate version.

Requires new authority: any material rewrite after challenge.

### Phase 2 — Sovereign alignment proposal

Privately compare the accepted public architecture with the sovereign internal
constitution, registries, agent catalogues, source-of-truth maps and execution
policies. Do not publish protected differences.

Exit condition: a private amendment/migration proposal is ready for the human
Judge.

Requires new authority: access, modification or ratification of sovereign
internal canon.

### Phase 3 — Registry and boot-packet pilot

Populate machine-readable registries and boot packets in one or more bounded,
non-production projections. Verify count semantics, authority references,
canonical precedence and truthful continuity.

Exit condition: pilot evidence and failure report exist.

Requires new authority: selection of projections and any write outside a draft
branch.

### Phase 4 — Model-routing and evaluation pilot

Bind exact, current model snapshots to Sol, Terra and Luna for a bounded test;
run applicable deterministic, model-based and human evaluations.

Exit condition: versioned evidence supports a promotion decision or records a
failed candidate.

Requires new authority: model binding, paid execution, external cost, protected
data use or live tools.

### Phase 5 — Activation proposal

Prepare the final V-COF 2.2 activation proposal with migration evidence,
rollback, revocation, documentation updates and seal plan.

Exit condition: explicit human ratification or rejection.

Requires new authority: merge, internal constitutional amendment and any live
activation.

## 3. Mandatory challenge questions

### Identity and terminology

- Is “Verittà Cognitive-Operational Framework” the sole canonical expansion?
- Is “contract-governed operations” correctly represented as an execution
  discipline rather than the acronym expansion?
- Are archetype, lineage, executable agent and runtime instance unambiguous?

### Versioning

- Can framework, constitution, engine, model, policy, proposal, ratification and
  seal versions be independently reconstructed?
- Does any document still infer governance changes from a model upgrade?
- Is `2.2` a bounded consolidation rather than an empirical maturity claim?

### Model routing

- Are Sol, Terra and Luna provider-neutral and risk-based?
- Are actual model snapshots separately ratified and reevaluated?
- Are independence claims invalidated when reviewers share the same family or
  inherited context?

### Memory and reinstantiation

- Does the boot packet carry sufficient authority, provenance and remaining
  state without dumping irrelevant history?
- Does every inherited record distinguish predecessor evidence from personal
  memory?
- Are revoked, superseded and conflicting sources visible?

### Effects and tools

- Is every tool action assigned its highest applicable effect class?
- Are targets, credentials, rollback and evidence adequate for that class?
- Can a sequence of small calls accidentally bypass a high-impact gate?

### Public/private boundary

- Could any generated public registry reveal protected topology or hierarchy?
- Do public documents avoid claiming operational completeness?
- Does internal sovereign canon remain precedent where the layers diverge?

### Evaluation

- Are fixture results clearly separated from behavioral and production-shaped
  evidence?
- Can a composite score hide an unauthorized action?
- Are negative results, reviewer disagreements and provider drift preserved?

## 4. Acceptance criteria for a future internal pilot

- exact candidate and engine/model versions are recorded;
- authority envelope and revocation path are testable;
- canonical-source conflicts yield review or block;
- critical unauthorized-action rate is zero in the ratified test scope;
- all metric components are reported separately;
- protected data stays within its approved boundary;
- rollback or containment is demonstrated;
- human review resolves critical and normative findings;
- failures are preserved rather than edited out of the evidence pack.

These criteria are planning requirements, not current results.

## 5. Rollback and revocation

Before merge or activation, every migration proposal must identify:

- prior canonical version;
- artifacts and projections affected;
- reversible and irreversible steps;
- revocation authority;
- evidence required to return to the prior state;
- records that must remain preserved after rollback.

The present drafting cycle is reversible by closing the draft pull request or
revoking its branch authority. It does not alter production.

## 6. Decision requested after challenge

After review of the draft PR, the human Judge should choose one of:

- `RETURN_TO_CHALLENGE`;
- `RATIFY_AMENDED_PUBLIC_CANDIDATE`;
- `AUTHORIZE_PUBLIC_MERGE`;
- `AUTHORIZE_PRIVATE_ALIGNMENT_PROPOSAL`;
- `REVOKE`.

None of these outcomes may be inferred from silence.
