# Propose & Ratify — V-COF Core 2.2

Proposal ID: `P&R-VCOF-CORE-2.2-2026-07`

Candidate version: `V-COF Core 2.2 RC`

Proposal state: `RATIFIED_FOR_DRAFTING`

Empirical status: `NO_RESULTS`

Repository layer: `PUBLIC_RESEARCH`

## 1. Proposition

Create a bounded V-COF Core 2.2 release candidate that consolidates public
framework semantics, provider-neutral model routing, portable operational
memory, machine-readable versioning, effect-aware tool governance and
evaluation-before-promotion.

The candidate is a design and migration proposal. It does not activate a live
framework release.

## 2. Rationale

Public V-COF research has matured beyond a single constitutional note. The
repository now contains a formal Propose & Ratify protocol, reinstantiation
ontology, VRI-Bench design, research-governance rules, synthetic pilot material
and an adversarial review. These components support a coherent public candidate
for the next bounded framework revision.

The candidate also addresses a general architectural problem: framework
version, constitutional revision, execution engine, model identifier, agent
lineage and runtime instance must not be collapsed into one version label.

## 3. Public grounding boundary

This proposal was informed by a read-only organizational review, but the public
record deliberately does not enumerate private repositories, internal agent
hierarchies, credentials, customers, live deployment details or unredacted
Forge records.

Publicly supportable claims are limited to:

- V-COF expands to Verittà Cognitive-Operational Framework;
- Propose & Ratify already exists as a versioned public protocol;
- reinstantiation and VRI-Bench remain pre-empirical;
- model/provider drift is a recognized research risk;
- public and sovereign internal sources have different authority;
- the human authority retains reserved decisions.

## 4. Proposed architectural deltas

### 4.1 Version separation

Represent framework core, constitution, engine generation, model snapshot,
policy, ratification and seal as separate, cross-referenced versions.

### 4.2 Provider-neutral routing

Define `sol`, `terra` and `luna` as risk/capability profiles rather than vendor
model names. Bind an actual model snapshot to a profile only through a
versioned routing decision.

### 4.3 Propose & Ratify lifecycle

Adopt the public lifecycle:

`DRAFTED -> PROPOSED -> CHALLENGED -> RATIFIED -> EXECUTING -> SEALED -> PUBLISHED`

Human authority may move an active record to `REVOKED`. Publication does not
imply empirical validation or live operational adoption.

### 4.4 Portable reinstantiation

Replace executor-specific memory assumptions with a minimum boot packet that
references current authority, jurisdiction, canonical sources, evidence,
remaining scope, model context and known debt.

### 4.5 Effect-aware tools

Classify effects as read-only, reversible write, external effect or
irreversible/high impact. Require stronger authorization and evidence as effect
severity increases.

### 4.6 Evaluation before promotion

Trigger relevant evaluations after material changes to models, prompts,
tooling, routing, memory schema or authority logic. No model judge or composite
score may independently approve a high-stakes promotion.

## 5. Candidate artifacts

The drafting cycle produces:

- a public Core 2.2 RC specification;
- a version manifest;
- a model-routing policy;
- a boot-packet schema;
- public ecosystem and agent registry schemas;
- an evaluation and promotion annex;
- a migration and challenge plan;
- a project agentic map;
- this bounded ratification record.

## 6. Explicit exclusions

The proposal does not:

- disclose or supersede sovereign internal canon;
- claim access to all organizational artifacts;
- enumerate protected organizational topology;
- activate engines, agents, tools or deployments;
- define vendor availability, price or performance as a current fact;
- treat a named agent lineage as numerical identity or consciousness;
- convert memory records into personal recollection;
- claim empirical validation;
- authorize merge or production mutation.

## 7. Acceptance criteria for this drafting cycle

The bounded cycle is complete when:

1. all identified artifacts exist in a dedicated branch;
2. YAML artifacts parse successfully;
3. relative links resolve inside the proposed repository tree;
4. public/private authority boundaries are explicit;
5. the proposal is presented in a draft pull request;
6. existing repository checks are allowed to run without weakened guardrails;
7. remaining challenges and reserved decisions are reported to the Judge;
8. no merge or production mutation has occurred.

## 8. Decisions reserved for a later ratification

- whether the proposal should be amended after challenge;
- whether any part should be merged into the public branch;
- whether sovereign internal documents should adopt corresponding changes;
- which actual model snapshots map to Sol, Terra and Luna;
- which operational projections, if any, enter a migration pilot;
- whether paid or live evaluation may begin;
- whether evidence eventually justifies V-COF 3.0.

## 9. Revocation and supersession

The human Judge may revoke this drafting authority at any time. A materially
changed candidate must receive a new version and renewed ratification; prior
approval cannot be inferred across versions.
